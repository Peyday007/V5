# Amendment 001 to the Brain Intelligence Map

**Amends:** `Brain_Intelligence_Map.md` (canonical working blueprint, 18 September 2026)
**Status:** Authoritative
**Date:** 18 September 2026

---

## Why this is an amendment and not an edit

The blueprint keeps its bytes and its hash. This file is registered as its own
source with `amends_id` pointing at it, so a promoted definition records which
of the two it read.

Rewriting the original would have been simpler and is exactly what CLAUDE.md §5
forbids: a source silently rewritten is a provenance chain that resolves to
something nobody ever actually wrote. Every canonical statement in the faculty
registry has to trace to a passage in a registered source, and that is only
true if the registered source is what was registered.

---

## 1. Faculty 14 is renamed and its scope is widened

Section 5.14 of the blueprint defines Faculty 14 as **Capability-Acquisition
Intelligence**, and the connection matrix and the final architecture statement
name it the same way.

It is expanded to **Capability Acquisition and Realization Intelligence**.

### What it owns

Faculty 14 owns the process of:

1. mapping a desired capability into Brain;
2. graphing the current and target topology;
3. identifying and acquiring the required knowledge;
4. compiling that knowledge into usable system contracts;
5. calculating implementation gaps;
6. directing construction;
7. proving the resulting capability;
8. registering it;
9. and improving the realization process itself.

### What changes about the original definition

The blueprint's acquisition loop — detect a gap, define the ability in before
and after terms, search internal registries, discover external candidates,
evaluate, prototype, test on a real bounded objective, register, route, monitor
and retire — is unchanged and remains correct.

What the amendment adds is that acquisition is not the whole of it. A capability
Brain cannot buy or install has to be **realized**: the gap between what is
declared and what exists has to be calculated against the running system, the
missing knowledge has to be acquired deliberately rather than assumed,
that knowledge has to be compiled into something a builder can act on, the
construction has to be directed, and the result has to be **proved** before it
is registered.

The original boundary still holds and is sharpened by the rename:

> Installing a tool is not automatically acquiring a capability. The new ability
> must be tested, understood, governed, registered, routable, and shown to
> improve a real objective.

Realization adds: **building software is not automatically acquiring a
capability either.** A merged pull request moves no dimension in the registry. A
capability exists when something that can be evaluated says it does.

---

## 2. What this amendment does not change

- The count remains fourteen faculties. This renames and widens one; it adds
  none.
- The Shared Executive remains a coordinating mind and not a fifteenth
  specialist department.
- Every other faculty's definition, boundary and connection is untouched.
- Nothing here grants any authority, widens any envelope, or authorizes any
  spending. Faculty 14 directing construction means composing a change request
  a person approves, through the mechanism that already requires that approval.
