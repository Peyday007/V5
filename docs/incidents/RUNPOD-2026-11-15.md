# RunPod GPU outage, 2026-11-15: diagnosis and permanent fix

## The questions, answered from production readings

1. **What stopped brain-vllm, and when.**
   - Pod `odsft6ptpi2reh` (Qwen/Qwen3-4B-AWQ, $0.19/h) was RUNNING at 08:27Z (cheap-lane run 43694589445).
   - Brain's own idle supervisor (`superviseRunpodPod`, 15 idle minutes) stopped it at about **14:10Z**. The 15:52Z report shows "stopped 1" and about 100 minutes stopped.
2. **Who did it.** Our idle scheduler did, as designed. It was not RunPod billing and not an infrastructure fault.
   - **The defect is what followed.** A stopped RunPod pod stays pinned to its host, and that host's GPU was taken by another tenant.
   - Every start since has been refused with `HTTP 500: start pod: There are not enough free GPUs on the host machine to start this pod.`
   - That is **109 refusals by 22:04Z**, with 30 research items waiting (run 43767406968).
   - The same thing happened on 2026-11-05 and 11-06 and ended only when the host happened to free up. The supervisor's only guard, "do not stop again after a refused start", forgets after the next successful start.
3. **Credentials.**
   - The production controller has a **valid** `BRAIN_RUNPOD_API_KEY`: RunPod answered every start with a reasoned refusal, not 401/403.
   - It does try to restart stopped pods.
   - It had **no path** for a host that cannot give the GPU back.
4. **The 404.**
   - It came from RunPod's **proxy** for a pod that is not running, on `/v1/models` too.
   - It was not vLLM, not authentication, and not a route that is meant to 404.
   - The probe misreported it as "auth: no-key request got HTTP 404 (want 401)".
5. **Why monitoring let it sit.**
   - The hourly `runpod-auto` run printed a **notice**, "did not answer its probe (stopped while idle, or down)", and exited **green** every hour.
   - The free-model fallback hid the outage from research, which kept running on the free models.
   - Nothing counted refused starts as an outage.
6. **Balance.** Not a factor. An earlier claim in this session that the balance was empty was wrong, and is withdrawn.

## The fix

- **Automatic recovery** (`server/services/cheap/runpodPod.ts`):
  - After 3 consecutive "full host" refusals with research waiting, the supervisor creates the **same recipe** on another host, within the price ceiling (`BRAIN_RUNPOD_MAX_USD_PER_HOUR`, default $0.24/h).
  - It points the lane at the new pod and deletes the stranded one.
  - Each step is a `RUNPOD_POD` row: `MIGRATED` (with the new URL), `OLD_POD_DELETED`, or `MIGRATE_FAILED`.
  - The lane's address is read from the newest `MIGRATED` row, so a restart keeps the new pod.
  - The workflow's `restore` then finds the new pod by name and reconnects the Fly secrets to it.
- **Honest monitoring** (`cheap-lane.yml` `runpod-auto`, `scripts/runpod-report.ts`):
  - A non-running pod is reported as its power state, and the probe is not run against it.
  - The report counts moves.
  - The run goes **red** (`runpod outage`) on 3 or more refused starts with nothing started or moved in the window.
- The idle stop is kept. The owner's Nov 5 design stands; it is now recoverable.
